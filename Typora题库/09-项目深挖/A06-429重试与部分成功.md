# 题 6：429 / 5xx / 超时 / 非 JSON 时怎么重试？和部分成功怎么拼？

## 面试官可能怎么问

- 哪些错误可重试？哪些不能盲重试？
- 10 语种 8 成功 2 失败，CMS 状态是什么？
- 为什么 429 不一定照搬 Retry-After？

## 口述结构（90 秒）

1. 可退：429/5xx/超时；不可盲退：schema/非 JSON
2. 部分成功：成功格立刻写，失败空，行仍草稿
3. 重试只打失败语种；禁止清全语种 API 做补空
4. Retry-After 不可靠则指数退避+抖动

## 参考答案

### 对应问 1：哪些可重试

| 错误 | 策略 |
| --- | --- |
| 429 / 5xx / 超时 | **可退**：当次不写 CMS，退避再试 |
| schema 错 / 非 JSON | **不盲重试**：换策略或进失败队列 |
| 4xx 业务拒绝（鉴权等） | 修配置/权限，不是盲退避 |

步骤（单 locale）：
1. 调模型/Dify
2. 解析 JSON → 失败则分类
3. 可退：sleep(退避) → 同幂等键再试
4. 不可退：记失败原因 → 队列/人工

### 对应问 2：8 成功 2 失败 CMS 状态

- 8 个成功 **locale 立刻写格**
- 2 个失败 **保持空**
- **整行仍草稿**；全语种齐才进待同步/发布态
- 重试**只打失败语种**，不动成功格

口述 40 秒：「失败不污染成功格；禁止用会清非根语种的 `update_zhcn` 做补空。」

### 对应问 3：为何不一定照搬 Retry-After

1. 网关/代理可能乱填或缺失 `Retry-After`
2. 多租户限流：照搬可能导致惊群或过久饥饿
3. 稳妥：`min(可靠 Retry-After, 指数退避上限)` + **抖动（jitter）**
4. 开口说清取舍：「我们以网关是否可信为准；不可信就自管退避。」


## 可能追问

- 限流按 key 还是租户？→ 看网关；开口说「按上游限流维度」，不编造。
- 死信怎么人工介入？→ 失败队列 + 运营重投；改进设计再谈。
- 幂等重试会不会重复计费？→ 同 idempotency 命中则跳过模型；否则可能计费，要监控。
