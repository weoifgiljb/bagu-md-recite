# 题 4：浏览器强缓存和协商缓存怎么工作？如何落地静态资源？

## 面试官可能怎么问

- Cache-Control 常见指令？
- Last-Modified 和 ETag 差别？
- HTML 和 JS/CSS 哈希文件策略如何分开？

## 口述结构（90 秒）

1. 强缓存：直接本地用，不发或 200 from cache
2. 协商：带条件头问服务器，304 或新内容
3. 静态资源 contenthash 长缓存；HTML 短缓存或不缓存
4. 更新靠换文件名，避免「用户一直旧包」

## 参考答案

### 1. 强缓存

响应头示例：

```http
Cache-Control: public, max-age=31536000, immutable
```

在有效期内，浏览器直接用本地副本（memory/disk），**可不请求服务器**。  
相关：`Expires`（HTTP/1.0），现代以 `Cache-Control` 为准。  
`no-store`：不存；`no-cache`：可存但用前必须协商；`max-age=0` 类似需再验证。

### 2. 协商缓存步骤

1. 强缓存失效或不允许直接用。  
2. 浏览器发请求带 `If-None-Match`（ETag）或 `If-Modified-Since`（Last-Modified）。  
3. 服务器判断未改 → **304 Not Modified**，体空，继续用本地。  
4. 已改 → **200** + 新正文 + 新校验头。

| 校验器 | 优点 | 注意 |
| --- | --- | --- |
| ETag | 内容级精确 | 集群要一致算法 |
| Last-Modified | 实现简单 | 秒级精度、内容变时间未变等边界 |

### 3. 工程落地（面试加分）

1. **打包**：`app.abc123.js` contenthash。  
2. **JS/CSS/图片**：`Cache-Control: max-age=31536000, immutable`。  
3. **HTML 入口**：`Cache-Control: no-cache` 或短 max-age，确保能拉到新 hash 引用。  
4. **API**：默认 `no-store`，避免用户数据进共享缓存。  
5. **CDN**：与源站缓存头一致；更新靠换 hash，少用「改同名文件」。  

```nginx
location /assets/ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}
location = /index.html {
  add_header Cache-Control "no-cache";
}
```

**业务例子**：Vite/Webpack 打 hash；AI 管理台发版后用户强刷 HTML 即可拿到新 JS，旧 hash 文件可逐步淘汰。

### 4. 发版与排障

1. 发版后用户仍旧：多半是 **HTML 被长缓存** 或 SW 未更新；先查入口文档缓存头。  
2. 静态 404：HTML 是新的，但 CDN 上旧 html 引用的 hash 已删——保留旧资源一段时间或用不可变缓存 + 延迟清理。  
3. 接口数据「改了但页面旧」：别给 JSON API 乱加长期强缓存。  
4. 调试：DevTools Network 看 Size 列 `(disk cache)` / `304`；Disable cache 仅开发用。  

对比协商 vs 强缓存：hash 文件名把「更新」变成「换 URL」，用户无需等待 304 判断，CDN 命中率也更高——这是现代前端默认策略。

## 可能追问

- Service Worker？→ 可精细控制缓存；要有更新策略，避免永久旧壳。
- from disk cache vs 304？→ 前者强缓存命中；后者走了协商。
- 小程序缓存？→ 还有包与 Storage 层；H5 web-view 才主要谈 HTTP 缓存。
