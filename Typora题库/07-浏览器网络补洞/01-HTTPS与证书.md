# 题 1：HTTPS 是什么？握手大致怎么走？为什么能防中间人？

## 面试官可能怎么问

- HTTP 和 HTTPS 差在哪？
- TLS 握手可以怎么口述？
- 证书校验失败常见原因？

## 口述结构（90 秒）

1. HTTPS = HTTP + TLS，传输加密、完整性、身份认证
2. 握手：换密钥 → 后续对称加密通信
3. 证书链 + 域名校验防中间人；本地抓包需信任伪证书
4. 小程序/现代浏览器均要求业务走 HTTPS

## 参考答案

### 1. 解决什么问题

明文 HTTP：运营商/Wi‑Fi 可窃听、篡改（注入广告）。  
HTTPS 提供：

1. **加密**：内容不可读。  
2. **完整性**：篡改会被发现（MAC/AEAD）。  
3. **认证**：确认对方是证书声明的站点（防假基站装你的站）。

### 2. 握手口述（简化步骤）

1. ClientHello：支持的 TLS 版本、套件、随机数。  
2. ServerHello：选套件；下发 **证书**（公钥）。  
3. 客户端校验证书链、域名、有效期、是否吊销（OCSP/CRL 等策略）。  
4. 双方推导出 **会话密钥**（经典 RSA 或主流 ECDHE 前向保密）。  
5. 之后应用数据用 **对称加密**（AES-GCM 等）高效传输。

面试不要求背字节，但要说清：**非对称用于认人与换钥，对称用于大宗数据**。

### 3. 证书与中间人

- 浏览器/系统信任根 CA；站点证书由中间 CA 签发，连到根。  
- 中间人若没有可信 CA 签的「你的域名」证书，校验失败 → 浏览器红警告。  
- Charles/Fiddler 抓 HTTPS：需安装并信任其根证书——等于你主动把中间人变成「可信 CA」。  
- 常见失败：过期、域名不匹配、链不完整、公司 SSL 解密代理、时间不准。

```text
浏览器 → 校验证书链与域名 → 派生对称密钥 → 加密 HTTP 请求
```

**业务例子**：微信小程序 request 合法域名必须 HTTPS；本地开发可开「不校验合法域名」，上线前必须配真证书。

## 可能追问

- HTTP/2、HTTP/3？→ 多路复用/QUIC；常跑在 TLS 上。
- 混合内容？→ HTTPS 页请求 HTTP 资源会被拦。
- 证书 pinning？→ App 更常见；Web 少用，运维成本高。
