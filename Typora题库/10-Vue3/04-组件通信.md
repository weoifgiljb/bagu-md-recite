# 题 4：Vue3 组件通信有哪些方式？怎么选？

## 面试官可能怎么问

- 父子、兄弟、跨多层分别怎么通信？
- props / emit、v-model、provide/inject、Pinia 怎么选型？
- 有哪些反模式（滥用 EventBus、任意 mutate props）？

## 口述结构（90 秒）

1. 按「距离」选型：父子 → props/emit；跨多层 → provide/inject 或 Pinia；全局业务态 → Pinia
2. 双向：`v-model` / 多个 `v-model:xxx`；或显式 update:prop
3. 插槽也能「通信」（父传模板，子决定渲染位置）
4. 反模式：改 props、全局 EventBus 满天飞、什么都塞 Pinia
5. 收尾：能 props 下钻就别上全局；配置型用 provide，业务态用 store

## 参考答案

### 1. 父子 / 兄弟 / 跨多层怎么通信？

| 关系 | 推荐 | 说明 |
| --- | --- | --- |
| 父 → 子 | props | 单向数据流；引用类型小心「子改父数据」 |
| 子 → 父 | emit / `v-model` | 事件上抛；表单控件优先 v-model |
| 兄弟 | 状态提升到共同父，或 Pinia | 不要先上全局总线 |
| 跨多层（主题、i18n、表单上下文） | provide / inject | 避免中间层无意义透传 |
| 跨路由 / 跨业务模块 | Pinia | 可调试、可持久化、DevTools 友好 |
| 父传 UI 结构 | slot / scoped slot | 模板级扩展，也是一种通信 |

口述时先问面试官「组件距离多远」，再给方案，比背清单更像实战。

### 2. props、emit、v-model、provide、Pinia 选型与代码

```vue
<!-- 子 Dialog.vue：标准 v-model -->
<script setup lang="ts">
const props = defineProps<{ modelValue: boolean; title: string }>()
const emit = defineEmits<{
  'update:modelValue': [boolean]
  confirm: []
}>()
function close() { emit('update:modelValue', false) }
</script>
```

```vue
<!-- 父 -->
<Dialog v-model="open" title="删除" @confirm="onConfirm" />
<!-- 多 v-model -->
<UserForm v-model:name="name" v-model:age="age" />
```

```ts
// provide：配置/上下文（对外只读 + 写方法）
import { provide, reactive, readonly } from 'vue'
const form = reactive({ name: '', errors: {} as Record<string, string> })
provide('formContext', {
  form: readonly(form),
  setField(k: string, v: string) { (form as any)[k] = v },
})
// 深子：const ctx = inject('formContext')
```

**选型口诀**：

- 一次回调、局部 UI → props + emit / `defineModel`（3.4+）
- 主题、国际化、表单上下文 → provide/inject
- 用户、权限、会话列表等跨页业务 → Pinia
- 仅本页的 `isOpen` → 留组件内，别进 store

### 3. 反模式与改法

1. **子直接改 props** → 本地拷贝编辑，确认再 emit；或 v-model。  
2. **props 钻孔五六层** → provide 或 store，中间层别只做搬运。  
3. **EventBus 满天飞** → 难追踪、易漏 off；改 Pinia action / 父回调 / 模块内有限 mitt。  
4. **UI 态全塞 Pinia** → 内存与订阅变复杂；跨页才进 store。  
5. **provide 可变对象随便改** → `readonly` + 收敛写方法，便于审计。

**业务例子**：IM 中列表 `emit('select', id)` → 父改 `activeId` props 给聊天面板；主题色 provide；当前用户与未读数进 Pinia。

**验收**：DevTools 能沿 props/events/store 看懂流向；改 A 不会通过隐式总线误伤 B；关键写路径有单一入口（action/方法）。

补充一条工程规范：公共组件库对外只暴露 props/emits/slots/少量 provide，不偷偷读全局 Pinia，方便在其它应用复用与单测。业务页面则相反，可以厚用 store。通信「能用」和「好维护」的分界，就是有没有清晰的单向数据流与单一写入口。

## 可能追问

- `defineModel`？→ 3.4+ 语法糖，等价 modelValue + update。
- `$attrs`？→ 透传未声明属性，包装组件库常用。
- provide 响应式？→ 传 `ref`/`reactive` 才响应；传普通对象则不。
