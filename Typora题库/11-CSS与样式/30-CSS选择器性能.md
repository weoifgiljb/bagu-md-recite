# 题 30：CSS 选择器性能还需要纠结吗？

## 面试官可能怎么问

- 从右向左匹配？
- 通配和深嵌套？
- 优化重点该放哪？

## 口述结构（90 秒）

1. 引擎匹配复合选择器大致**从右向左**：先找关键，再滤祖先
2. 过深后代、宽泛 `*`、长链在超大 DOM 上更贵，但现代引擎通常很快
3. 真正瓶颈常在：样式体量大、无效属性、强制回流重绘、动画踩 layout
4. 实践：类名清晰（BEM/CSS Module）、少「为微优化牺牲可维护性」

## 参考答案

### 1. 从右向左匹配（怎么答）

选择器 `.nav ul li a span` 可以理解为：

1. 先找出所有 `span`；  
2. 再看它是否在 `a` 里；  
3. 再向上是否满足 `li → ul → .nav`。

关键越宽（如 `*`、`div`、`span`），早期候选集越大，后面过滤越累。

```css
/* 关键宽，链又长：不推荐 */
.sidebar div ul li a span { color: red; }

/* 关键是明确类：更好维护，一般也足够快 */
.sidebar__link-label { color: red; }
```

### 2. 通配 `*` 与深嵌套

```css
* { box-sizing: border-box; } /* 全局一次可接受 */
.card * { margin: 0; }        /* 卡片内所有后代都扫，尽量少用 */

/* 过深 */
.a .b .c .d .e .f { ... }
```

建议：
- 全局 reset 的 `*` 可以保留（一次、可预期）。  
- 业务样式优先**单类**或浅层；用 CSS Modules / scoped 避免互相误伤。  
- 不要为了「性能」写成无法维护的短类沼泽，也不要 6 层后代选择器。

### 3. 优化重点该放哪（比纠结选择器更重要）

| 优先级 | 问题 | 做法 |
| --- | --- | --- |
| 高 | 大面积 layout/reflow | 少读布局属性；动画用 `transform`/`opacity` |
| 高 | 巨型 DOM + 频繁改 class | 虚拟列表；批量更新 |
| 中 | CSS 体积、无用规则 | 按路由拆分、删死码 |
| 低 | 选择器微优化 | 类名清晰即可，别过度 |

```css
/* 列表项动画：改 transform，而不是每帧改 top/width */
.item.is-active { transform: translateX(4px); }
```

```js
// 避免
items.forEach(el => { el.style.width = el.parentElement.clientWidth + "px"; });
```

### 4. 工程实践一句话

组件里用 **BEM / 模块类名**，比 `.a .b .c .d span` 好维护；列表里避免每帧改 style。选择器性能是加分题，**回流与包体**才是主战场。

## 可能追问

- `:has()` 贵不贵？→ 相对更贵（要看子孙），别在超大 DOM 上滥用。
- 关键 CSS？→ 关键**关键路径 / 拆包**，不是把类名再缩短两个字符。
- `getComputedStyle`？→ 可能触发同步布局，热路径慎用。
