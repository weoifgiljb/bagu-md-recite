# 题：Flutter 列表性能与卡顿怎么排查、怎么优化？

## 面试官可能怎么问

- ListView 和 ListView.builder 区别？
- 列表卡顿常见原因有哪些？
- 你怎么系统排查一帧掉帧？

## 口述结构（90 秒）

1. builder/懒加载：只建可视区附近子项
2. 常见因：主 isolate 重活、原生子项过重、图片未缓存、无key乱复用
3. 排查：Performance Overlay / DevTools Timeline → 定位 build/layout/paint/IO
4. 优化：builder、itemExtent、缓存图片、Isolate、拆 widget、RepaintBoundary

## 参考答案

### 对应问 1：ListView vs builder

- `ListView(children: [...])`：一次性把所有子 Widget 建出来 → 长列表爆炸
- `ListView.builder` / `SliverList`：**按需**创建可视区附近 item
- 固定高度可设 `itemExtent` / `prototypeItem`，加速 layout

步骤（长列表）：
1. 数据层分页或懒加载
2. UI 用 `ListView.builder`
3. 稳定 key；item 内避免在 build 里做重计算

### 对应问 2：卡顿常见原因

1. **主 Isolate 干重活**（巨 JSON、同步编解码）
2. item 太重：层层嵌套、每行解码大图、同步读盘
3. 整表 `setState`，列表外父级重建把 list 一起扛上
4. 图片无缓存、无占位，滚动时反复解码
5. 错误 key → 复用错乱 → 额外 rebuild
6. 透明/阴影/裁剪导致过度绘制

### 对应问 3：系统排查步骤

1. 复现：打开 **Performance Overlay** 看 UI/GPU 条是否爆
2. DevTools **Timeline**：看卡在 build / layout / paint / JS-like Dart / 原生
3. 若 build 久：缩小 rebuild（拆 Stateful、`const`、状态下沉）、检查 item build
4. 若算力久：搬到 **Isolate**
5. 若 paint 久：`RepaintBoundary`、减透明度/阴影、图片尺寸匹配
6. 若桥接久：降 Platform Channel 频率，传路径而非巨 blob

**优化清单（口述可报）**
- `ListView.builder` + `itemExtent`
- `CachedNetworkImage` / 预解码合适分辨率
- item 拆成 `const` 子组件；父级别乱 `setState`
- 重计算 `Isolate.run`
- 监控页 2000+ 点：聚合 + 虚拟化，不一次灌

**业务例子**：端内监控/会话列表滑动掉帧 → Timeline 发现 item build 里同步格式化 → 预计算 + builder + 图片缓存后恢复 60fps。


## 可能追问

- GridView 一样吗？→ 同样用 builder/Sliver；注意 crossAxis 计算成本。
- AutomaticKeepAlive？→ 保状态但吃内存；Tab 多页慎用。
- 和 React 虚拟列表类比？→ builder ≈ 窗口化；Element 复用 ≈ fiber/reconcile。
