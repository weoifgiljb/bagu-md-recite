# 题 2：从前端角度如何「预防」越权？

## 面试官可能怎么问

- 前端能防越权吗？
- 路由守卫够不够？
- 你会做哪些配合措施？

## 口述结构（90 秒）

1. 结论先讲：前端不能单独防住，只能降风险 + 配合后端
2. 路由守卫、按钮权限、请求封装是「篱笆」不是「门锁」
3. 关键是服务端鉴权与资源归属校验
4. 前端可做：少泄露、强制走网关、错误态、复检

## 参考答案

### 1. 前端能防越权吗？

能做的是：**减少误用、减少信息泄露、保证走正规请求链**；不能做的是：在浏览器里保证「攻击者绝对调不到接口」。  
面试一句：**门锁在服务端；前端是导视牌和围栏。**

### 2. 路由守卫够不够？

不够。守卫只拦「进页」，不拦：  
- 已打开页面里的按钮/请求  
- 直接调 API  
- `keep-alive` 缓存页被再次激活  

步骤（更稳）：  
1. `beforeEach` 鉴权 + 角色  
2. 页面 `onMounted`/`onActivated` 再拉权限快照  
3. 写操作前二次检查；`403` 统一收口  

```ts
router.beforeEach(async (to) => {
  if (to.meta.requiresAuth && !getToken()) return '/login'
  if (to.meta.roles && !hasRole(to.meta.roles)) return '/403'
})
```

### 3. 前端配合措施清单

1. **权限指令/组件**：无权限不渲染危险入口（仍要后端拦）  
2. **请求封装**：统一带 token；禁止把「仅前端算出来的 isAdmin」当真理  
3. **少在 URL/本地塞敏感权限标记**（可伪造）  
4. **错误处理**：`403` 不继续乐观更新；列表不展示越权数据空洞时乱补  
5. **联调契约**：每个写接口文档写清「校验资源归属」  
6. **自测**：改 id、换角色账号、重放  

业务例子：设置页隐藏菜单后，深链进页应被守卫 + `onActivated` 复检拦下；导出按钮隐藏的同时，导出 API 必须 403。

- 为什么不能信 localStorage 里的 roles？→ 用户可改。
