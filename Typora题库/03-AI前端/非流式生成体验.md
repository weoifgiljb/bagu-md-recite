# 题 8：非流式接口如何做出「还在生成」的体验？

## 面试官可能怎么问

- 后端一次性返回整段 reply，前端怎么避免「干等无反馈」？
- 假打字机、骨架屏、可停止，各自边界是什么？
- lab delay 开关对前端有什么意义？

## 参考答

**现实**：很多内部/演示接口（含当前 `POST /api/ai/chat`）是**非流式**的；产品仍要做出「正在想/正在写」的体感。

**可用手段（由轻到重）**
1. **请求中态**：禁用发送、按钮变「生成中…」、assistant 占位气泡 + 三点动画/骨架。
2. **假打字机**：整段 `reply` 到达后，前端按字符/词节流展示。注意：这是**展示层动画**，不是真流式；停止只能停动画，省不下已消耗的后端时间。
3. **分阶段文案**：先显示「检索文档中…」再「组织回答…」（若后端有阶段事件更好；没有就前端时间片模拟，需诚实，别伪造进度百分比）。
4. **可停止的边界**：`AbortController` 取消 HTTP → 真正中断等待；若响应已返回、只在播假打字机，停止 = 立刻展示全文或截断动画并标记 `stopped`。

**不要做的**
- 把假打字机说成 SSE 流式（面试会被追问穿帮）
- 无上限转圈无超时提示（应有超时文案与重试）

**lab delay**：后端可人为延迟，方便前端验收 loading/骨架/取消；联调时打开，生产关闭。

**业务例子**：文档审阅助手一次返回 reply+matches——先出骨架与「检索中」，返回后假打字机播 reply，同时 matches 列表可先出现（用户可边看引用边等字出完）。

## 可能追问

- 假打字机如何避免和 React 严格模式双调用冲突？→ 用 effect 清理 timer / 生成 epoch。
- 为何还要做真流式？→ TTFT、可中途停止省 token、长文不必等全完。
