# 题 7：掉帧、长任务、强制布局（forced reflow）在 DevTools 里怎么定位？

## 面试官可能怎么问

- 60fps 和 16.7ms 什么关系？
- 什么是强制同步布局？火焰图里长什么样？
- 大列表卡怎么验证是渲染问题还是 JS 问题？

## 口述结构（90 秒）

1. 一帧预算约 16.7ms；超时就掉帧
2. Performance 看 FPS 红条 + Long Task
3. 强制布局：Script 中间插入 Layout，读几何又写样式
4. 大列表：虚拟化 / 分页；改完对比两次录制

## 参考答案

### 1. 掉帧怎么确认

1. Performance 录制滚动或动画。
2. 看顶部 **FPS** 条：变红、变空表示没稳住 60。
3. **Frames** 轨道里个别帧变长。
4. 对应时间片里 Main 是否被宽黄条占满。

心里换算：16.7ms 内 ideally 做完输入处理 + JS + 样式 + 布局 + 绘制；超过就容易卡。

### 2. 强制同步布局（Layout thrashing）

模式：在同一轮 JS 里 **写 DOM/样式 → 立刻读几何**（或反过来反复），浏览器不得不提前算布局。

危险 API 例：`offsetHeight`、`getBoundingClientRect`、`scrollTop` 等，夹在多次样式写入之间。

```js
// 坏：循环里读写下发
items.forEach((el) => {
  el.style.width = box.offsetWidth + 'px' // 读 + 写交错
})

// 好：先读完再写，或批到一次性 class 变更
const w = box.offsetWidth
items.forEach((el) => { el.style.width = w + 'px' })
```

火焰图特征：黄色 Script 中间反复插进紫色 **Recalculate Style** / **Layout**。Event Log 里也能看到。

### 3. 大列表 / 对话流卡顿实操

1. 录制：快速滚动列表或流式输出时狂刷 DOM。
2. 若 Self 热点在框架 patch / 你的 `renderItem`：减节点、memo、虚拟列表。
3. 若热点在 `JSON.parse` 大包：接口分页/瘦字段。
4. 若 Layout 占比高：减复杂 CSS（blur、大阴影）、避免每帧读布局。

AI 打字机场景：不要每个 token 都重排整个消息列表；只更新最后一条气泡文本节点。

### 4. 验证闭环

1. 同一操作路径录制，导出或截图 Summary 占比。
2. 改代码后再录一次。
3. 对比：Long Task 数量、Scripting 总时间、FPS 是否改善。

面试加分：能说出「用 Performance 对比两次，而不是凭感觉」。

## 可能追问

- requestAnimationFrame 一定不卡吗？→ 只保证「对齐帧」；回调太重照样 Long Task。
- CSS 动画一定走合成线程？→ transform/opacity 易吃合成；改 width/top 容易触发布局。
